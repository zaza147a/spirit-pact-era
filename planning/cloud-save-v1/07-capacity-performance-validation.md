# 07｜500 人容量與免費負載的驗證計畫

## 單一實際角色的已量測事實
- 原 JSON：**46,736 bytes**（含縮排）。
- 緊湊 JSON：**27,518 bytes**。
- bag：5,823 bytes／61 條（20 uid 裝備、41 stacks）。
- gear：2,442 bytes／10 件。
- pets：2,856 bytes／3 隻；寵物穿戴裝備 6 件。
- cards：2,044 bytes／76 stack。
- battleHistory：7,427 bytes／12 筆（單獨保留、有限留存）。
- autoSellJunk：3,770 bytes／228 ID，可考慮獨立設定且只在設定改動時保存。
- 同一檔案的裝備 UID：36 件唯一；此檔無重複。

## 4,000 格角色估算（注意：未包括 DB overhead）
| 模型 | 4,000 格 |
|---|---:|
| 全部使用原縮排 JSON | 178.28 MiB |
| 全部使用緊湊 JSON | 104.97 MiB |
| 除去 battleHistory | 76.58 MiB |
| 除去 battleHistory 與 autoSellJunk | 62.13 MiB |

該樣本已包含大量材料卻只有 41 個堆疊種類；相反，若玩家囤積數百件有獨立詞條的裝備，容量會隨 **裝備實例數** 增長。且共用倉庫與資料庫索引尚未列入。

## 實測測試集
1. **基礎型**：500 帳號，平均 2 格／帳號，平均 10 件獨立裝備、1 隻寵物。
2. **完整型**：500 帳號×8 格，依本次檔案生成 4,000 角色，所有 UID 更換為唯一的測試用 UUID，不能直接複製實際玩家 UID。
3. **重度囤積型**：4,000 角色，每格分別設 100、300、500 件獨立裝備，並加入共用倉庫。
4. **極端戰鬥型**：24h 離線單角色大量擊殺、掉落與自動分解，測試結果寫入 DB 的資料量及回應時間。
5. **安全型**：跨裝置重複領取、相同 UID 複製、同裝備同時背包/倉庫、舊版 JSON 偽造，期待全部拒絕。
6. **工作量型**：500 人短時間集中登入並結算，實測 Worker CPU、D1 rows read/written、請求總數、429/5xx、完成延遲。

## 免費方案的硬性約束
目前候選為 Cloudflare Workers/D1 免費額度與獨立免費身份提供者。免費 Workers 每次 10ms CPU 限制使完整 24h 精確戰鬥演算有重大風險；必須以實際程式測試分段結算與重送機制，不能承諾 500 人 100% 免費且可隨時一次結算完成。

## 建議觀察指標
- 角色 P50/P95/P99 序列化位元組數；個人倉庫尺寸及裝備 UID 數。
- SQLite 實際檔案大小、D1 儲存已使用%、索引比例、每次交易讀寫列數。
- `event_ledger` 每月增量、戰報截斷／刪除策略。
- 單筆離線 24h 需切割的事件數、HTTP 次數、CPU 累計與處理完成時間。
- 大量請求下失敗不漏獎，且重試不重複發獎。
- 50%、75%、85% DB 空間使用警戒線；達警戒先調整儲存或分庫，不能丟棄玩家物品。

## 結論
**只按本樣本推算，單庫看起來有機會；但不能據此保證。** 先將容量實測器及資料庫負載測試加入開發分支，在 staging 完成 500×8 實際寫入，再決定單庫或以 account_id 分庫。正式版目前不做任何改動。
