# 02｜全部物品雲端化：資料結構與容量

## 正式資料必須上雲
帳號、8 格角色、人物能力與技能、寵物所有階段（含融合人形 S/SS/SSS）、寵物裝備、卡片、刻印、角色背包、共用倉庫、消耗品數量、貨幣、任務／試煉／首領進度、掛機設定與可領獎勵。**不得以本機 localStorage 作為正式資產來源**。

## 正規化建議
- `accounts`：帳號、身份提供者 subject、狀態、建立時間。
- `characters`：account_id、slot_index(0..7)、ruleset_version、save_version、等級、配點、位置、角色狀態、快照。
- `inventories`：角色或帳號倉庫位置、分類、數量與 version。
- `item_stacks`：每種同質可堆疊物品一筆 `(owner, item_id, qty)`，例如藥水與材料。禁止為 9999 個紅水新增 9999 列。
- `equipment_instances`：每件具有隨機詞條、階級、卡片或強化的裝備一筆唯一 ID；保存 item_id、隨機值、強化階段與所在位置。
- `pets`：每隻寵物獨立 UUID，保存角色歸屬、四系／稀有度／進化階段／融合方向／忠誠／人形階段／技能／能力與裝備。
- `shared_warehouses`：每帳號共同倉庫，角色間轉入／轉出必須原子化。
- `offline_sessions`：離線規則快照、起點、結算進度、seed、狀態。
- `event_ledger`：防重複請求及補償事件，保留必要摘要與保存期限。
- `game_rule_versions`：物品基本定義、戰鬥公式、掉落及資料模型版本。固定遊戲美術/說明不重複放入每一筆存檔。

注意：D1 採 SQLite；物品的正規化與 JSON 欄位比例應透過查詢模式、寫入成本與實際存檔量測決定，不能一律拆分成海量小列，也不能一律維持整包 JSON。

## 500 人容量模型
總角色數上限 = 500 × 8 = **4,000 格**。以下是未測量前的粗估、不是實際檔案量：

| 平均每格未壓縮資料 | 4,000 格資料 |
|---|---|
| 20 KiB | 78.1 MiB |
| 50 KiB | 195.3 MiB |
| 100 KiB | 390.6 MiB |
| 200 KiB | 781.3 MiB |

單格 100 KiB 時，光角色本體已接近 D1 免費單一資料庫 **500 MB 上限**；加上索引、帳號倉庫、寵物、事件帳本及資料庫開銷就可能超出。因此不應保證「500 人全部八格一定塞進單一免費 D1」。需量測 **現有最大 10～50 份真實存檔**、裝備實例數、寵物數及倉庫尺寸，建立 P50／P95／P99 分布。

## 容量保護
1. 倉庫／背包使用物品 ID + qty；數量超過上限時拒絕，不可整數溢位。
2. 一件隨機裝備一個唯一 ID；防止同 ID 同時出現在背包、裝備欄與倉庫。
3. 自動分解在可信結算中執行；存檔只保存剩下的物品，不永久保存每次戰鬥明細。
4. 裝備定義／圖片／共鳴說明共用，不在玩家資料重複寫入。
5. 每次保存改動部分資料或合併事件；必要時定期建立權威快照，並清理符合保留策略的舊事件。
6. 設定資料庫空間水位（例如 60%、75%、85%），超過時通知管理員；絕不默默丟棄玩家裝備。
7. 單庫接近上限時評估依 account_id 分庫（交易與倉庫皆在同一帳號範圍），但跨庫管理、備份及部署會增加複雜度。
8. 備份空間另計；驗證備份可在隔離環境成功還原。

## 資料量量測與驗收
- 建立只讀掃描工具，統計現有角色 JSON 的位元組數、裝備件數、物品種類、stack 數、寵物數、倉庫大小。
- 以 500 帳號×8 格的 P95／P99 合成負載實際寫入測試 D1，量測資料庫總大小、索引、讀寫列數與耗時。
- 測試角色切換、裝備替換、倉庫轉移、寵物融合、稀有掉落、1000 次連續掛機結算；檢查 UUID 唯一、總資產守恆與冪等。
- 驗收不得只用「JSON 字串長度 × 人數」代替資料庫實際容量。

## 免費方案風險
現有 Cloudflare D1 免費方案有單一資料庫容量限制及帳號總容量、讀寫額度，實施前需重新核對官方最新限制；免費不是 SLA，也不應依賴不可恢復的單一雲端資料庫。
